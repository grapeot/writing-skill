# 中文外部文章写作（External Writing）

## 元数据

- **类型**：Workflow
- **适用场景**：把已经核实过的调研成果，转成面向读者的中文分析文章或公开报告
- **前置依赖**：`workflow_deep_research_survey.md` Phase 1-3 或等价的已核实事实底稿
- **关联 Skill**：`antigravity_cli.md`、voice-lora rewrite skill、`external_prose_lint.md`、`bestpractice_external_prose.md`、GPT Image 生成 skill
- **最后更新**：2026-10-26

## 目标

把已核实的调研写成一篇中文 external 文章：读者读一遍就能抓住thesis，读着不累，不像AI写的，每个事实都能追溯到来源。

## 验收标准

所有验收标准都在最终的`article.md`文件上判定，主线程不能自评通过。

1. **选题与开头合格**
    - 动笔前在 `brief.md` 中写下一句话、可证伪的 thesis，以及相对作者既有文章和公开报道的信息增量。
    - 用 `timeout 60 rg` 检索作者既有文章的中文归档（位置见工作区 overlay），确认 thesis 不与近期文章重复。
    - 开头先回答读者为什么想读：`brief.md` 写明读者是谁、他此刻已在关心什么（他自己的问题，不是我们的话题）、我们从哪一点接上，至少比较两个入口再选。门槛测试：列出读者须同时满足哪些前提才会被开头吸引，超过两项就换入口。入口必须是正文兑现的东西，不以诱饵换题。
    - 有站点历史流量时，查同类题材旧文的流量分位，验证所选入口类型读者是否买账。实测「这东西跟我有什么关系、我能不能用」类入口的文章普遍落在高分位，拆机制类大多在中位数附近或以下；标题挂热门主体不等于有流量。
    - 标题自明，读者初看即知主语和讨论的问题；导语每句话都给读者继续读下去的理由；数字首次出现前先交代测量对象。
    - 骨架问题驱动，不按清单罗列：`brief.md` 的 H2 规划写成读者会问的问题或设计者要回答的挑战，不写成对象名。分析一个系统、产品或技术决策时，按「遇到什么挑战 → 要达到什么目标 → 做了什么决定 → 每个决定换来什么、付出什么」组织；技术事实作为决定的后果出场，不先列组件再讲各自在哪有用。主线程在把 brief 交给 Argon 之前按这条检查骨架。
2. **事实零漂移**
    - 用独立上下文对照 `source_contract.md` 逐条核查最终稿（即 voice rewrite 之后的文本）。
    - 数字、日期、归属、方向、判断强度、新增或遗漏事实的漂移数为 0。只验收最终文本。
    - 主线程逐条裁定核查结果。独立核查员常把 `brief.md` 有意集中到一段的限定说明报成「限定被删掉」，并建议把限定挂回每句；按 brief 的设计判定这类不是漂移，否则会把调研 memo 写法带回正文。
    - 重写时引入了解释性常识或新的来源事实，先补进 `source_contract.md` 再送核查，否则核查员会把它们报成新增事实。
    - 核查员对删除型漂移不敏感（voice 删掉一个身份交代或一个限定，句子照样通顺）。核查时同时给出 voice 前的版本，要求逐段对比有没有丢掉事实或限定。
3. **机械校验（lint）阻断通过**
   - 在最终稿上运行校验命令：
```bash
.venv/bin/python -m writing_skill.external_prose_lint_cli article.md
```
   - 最终稿需满足 `hard_findings=0` 且退出码为 `0`，提交时附 stdout 全文。
   - voice rewrite 后若仍有 hard findings，由主线程进行最小机械修正（改标点、禁词替换、拆 `当……时`），不改其余文字；无法机械修正的段落重新 run voice rewrite。
4. **独立冷读通过**
   - 由调用方 harness 新开 fresh-context sub-agent 执行（Claude Code 用 Agent/Workflow，OpenCode 用其 subagent；模型就用调用方的主力模型，不必是 Claude），不用 Antigravity，也不能由编排流程的主线程或管线 agent 自己读。sub-agent 只拿到最终正文（内联或唯一的文件路径）和下面固定的评测 prompt，不给 `brief.md`、`source_contract.md` 或历史对话。Argon 负责写，评测换成逻辑更强、没见过任何上下文的读者。
   - 冷读跑一次即可。早先观察到的大幅波动（同一稿 19 / 2 / 18）来自 Antigravity；换成 fresh-context sub-agent 后，同一稿三次判定一致（22 / 13 / 20 全 BLOCK，10 / 11 / 11 全 BLOCK），且点中的是同一批句子，不需要多跑取中位数。
   - 最后一行必须是 `TERMINAL_VERDICT: SHIP`。如果每千字回读点超过 1 处、口吻像汇报/研究报告/说教、复述不出 thesis、有逻辑断点、说不出进入理由或进入理由要叠加多个前提才成立，则判 `BLOCK`。
   - 回读密度由主线程机械计算：`REREAD_COUNT` 除以正文汉字数（千字）。评测模型给出 `SHIP` 但计算结果超过每千字 1 处时，按 `BLOCK` 处理，不采信 verdict 行。
   - 冷读 prompt 模板：
```
只读给你的这一篇文章（内联在下方，或只读指定的这一个文件），不要读其他文件、不要搜索、不要写文件。只在回复中输出评测结果。
你是一个普通上班族，在地铁上用手机读这篇文章。你没读过任何相关报道，注意力有限，每句只读一遍，不回看。
1. 逐段标出所有让你停下来、回读、或读完没抓住意思的句子，说明卡在哪（太长、定语太多、术语没解释、指代不清、和上文接不上、作者在讲自己的工作过程）。
2. 口吻：读起来像朋友跟你讲一件事，还是像下属给老板汇报、像研究报告、像说教？举例。
3. 用大白话一句话说出文章的核心观点，再每节一两句复述。
4. 逻辑断点：未介绍就评价、提出的问题或数字没回收、话题来回跳。
5. 进入理由：只看标题和导语，以下面这位读者的身份说出你为什么会继续读。读者身份：<一行目标读者描述，不写 thesis>
最后两行：`REREAD_COUNT: N` 和 `TERMINAL_VERDICT: SHIP` 或 `TERMINAL_VERDICT: BLOCK（原因）`。
===== 文章 =====
```
5. **文风改写完成**
   - 最终稿已经过 voice rewrite，且每个 `kept_original` 段落都经过了审阅。
   - （可选）记录 `voice-lora compare` 给出的 AI 味分数。

## 失败了怎么修（含顺序约束）

成文与验收必须遵守这一顺序：**Argon 起草 → voice rewrite → 主线程事实核查（收回漂移）→ 最终稿跑 lint 和冷读**。

为什么是这种顺序：
- 除了Argon以外没有写得不那么差的中文模型，所以正文必须由Argon起草。
- voice rewrite能显著减少AI文风，但是它是小模型，会引入事实漂移，还会把句子改长、加回禁词和破折号。
- 必须在voice rewrite以后由主线程核查事实并收回漂移，然后在最终稿上用lint拦截改不掉的标点和禁词习惯，用冷读验收普通读者的阅读体验。

当验收不通过时，我们在最低层进行修复：
- **事实漂移**：主线程进行手术式修正，仅改动事实点，保留 voice rewrite 后的措辞，并逐条记录 `原句 → 修正`。
- **lint hard 命中**：主线程进行机械最小修正，或者对该段单独重跑 voice rewrite。
- **冷读 BLOCK（负担、口吻、逻辑）**：将冷读意见和对应段落交给新的 Argon 会话重写该节，然后对重写部分重新跑 voice rewrite、核事实和重跑 lint 及冷读。主线程不自己改写句子。
  - 冷读点名的是具体句子时，给段落编号，让 Argon 只重写被点名的段落，未点名段落一字不动。
  - 只把实质性重写的段落送 voice rewrite；只删改一两句的段落直接用 Argon 输出。已经过 voice 的文字不再送 voice，按段落序号拼回全文。
  - 第一轮 BLOCK 是常态，不必推倒重来。实测按这个办法局部重写两轮，回读点从 10 处降到 5 处再到 1 处。
  - 局部重写的补丁如果都是在加解释、加限定，连续两轮回读点不降反升，就停止逐条修补，改做减法：下调该节字数预算（实测约砍四分之一），删掉次要事实和作者个人数据，再让 Argon 按新预算重写该节。实测逐条修补三轮回读点从 4 处涨到 10 处，减法重写一轮即通过。
- **选题或 thesis 不成立**：退回修改 `brief.md`。

## 角色边界

- **主线程**：编辑/事实负责人。负责确定thesis、准备`source_contract.md`和`brief.md`、核查事实、做lint的机械最小修正、裁定是否交付。主线程不自己写正文，也不按个人语感回改voice rewrite输出的文风。
  - 写 `brief.md` 时和交付前，主线程以目标读者身份回答三个问题：为什么会点进来，读到哪里会停下，读完带走什么。答不上来就回到选题和入口，不进入起草或交付。这一步只用来在跑 gate 之前拦住选题与入口问题，不替代冷读，也不算主线程自评通过。只核对流程是否齐全而不以读者身份读文章，框架问题会一直漏到最后。
- **Argon (`gemini-4-argon-high`)**：负责起草正文，以及按冷读意见重写未通过的章节。
- **voice rewrite**：负责文风改写，减少AI文风。
- **lint与冷读评测者**：负责在最终稿上做结果判定。冷读者是调用方 harness 的 fresh-context sub-agent，不是 Argon。

## 方法建议

以下建议非强制，agent 可以按文章情况自行调整：

- **每节最多 3 个核心事实**：限定说明和未知信息合并成一段（专门交代目前不知道的事），不在每句里挂限定条件。
- **Argon 句式目标**：目标首位写明一句只说一件事、先具体再判断、长定语拆短句。附 1-3 个 before→after 例子。可用：
  - Before：`新版增加例外：用户选择把这些数据提供给其他支持个性化广告的 Google 服务`
  - After：`新版加了个例外。如果你自己把这些数据开放给 Google 的其他服务，而那个服务本身有个性化广告，这句承诺就不管用了。`
- **每节字数预算**：给 Argon 的 prompt 写明每节字数预算。为了降低阅读负担，允许删掉次要事实。
- **先写为什么读者要关心**：每节先写读者为何要关心。先介绍对象再评价。前文数字/问题后文回收。主线给足篇幅，旁支压成一句。
- **术语先解释再使用，一物一名**：`brief.md` 列出读者禁区术语，每个术语写明第一次出现在哪一节、用哪个固定说法，写进 Argon prompt。冷读最常卡的就是术语在解释之前已被使用，以及同一对象换着名字叫。
- **一个例子只证明一个论点**：`brief.md` 每节的事实条目写明它证明哪句话。例子和挂着的论点对不上（比如用对照组的变化去证明实验组的优势），或一个例子同时被拿来证明两件事，冷读会报逻辑断点；换例子或拆开写。
- **作者一手经历只当证据**：作者自己的实测、设备和经历不做入口。每条在 `brief.md` 里写明它回答读者的哪个问题，回答不了的不进正文；进正文的一节最多用一两次。
- **动笔前核一次第三方现状**：对正文点名的第三方项目，其定性（是什么、支持什么）和流传数字的口径，在写 `source_contract.md` 时做一次现状核查。调研 memo 只有几天时效，项目定性和标题数字的口径常与流传说法不同。
- **中文先行**：引第三方原话中文先行，英文原文最多一句。
- **来源就地嵌入**：正文就地嵌入 `[中文锚文本](url)`，全文至少 3 个，同一 URL 最多 2 次，文末不设参考资料章节。

## 已知陷阱

以下是真实发生过的故障：

- **冷读只问复述，测不出阅读负担（2026-10-26）**：评测模型理解力很强，只问能不能复述、逻辑通不通，永远能过，量不出普通读者的阅读负担。
- **用 Argon 冷读，自己写的问题自己看不出（2026-10-26）**：同一篇稿子（其中有作者读完说「看不懂」的三层结构定义段），Gemini 冷读给出 REREAD_COUNT 0、SHIP；三个 fresh-context Claude sub-agent 各读一次，回读点 22 / 13 / 20，全部 BLOCK，且都点中了那段定义、一句反驳没人提过的说法、导语要叠两个前提的问题，和作者的判断一致。Gemini 对另一份候选稿连跑三次得到 19 / 2 / 18，判定来回翻。写和审用同一个模型时，审的人对自己的写法没有免疫力；逻辑判断也不是 Argon 的强项。
- **删除型事实漂移漏过核查（2026-10-26）**：voice 删掉了导语里「开源推理引擎」这一身份交代，又把「不能说天然低延迟」改成「这并不意味着低延迟」，两轮独立核查都没报，是冷读读者说「不知道 SGLang 是什么」才暴露。
- **按 what 罗列写成说明书（2026-10-26）**：先介绍系统有哪几层、哪些组件（「阶段层负责……；会话层……；连接图描述……」），再逐个讲在什么场景下有用。读者被迫先记一串名词，不知道为什么要记，作者评价「看不懂，cognitive burden 太高」。改成站在设计者位置：先讲挑战和目标，再讲由此推出的决定，组件名能删就删。同类问题：先立一个分类框架再往里填内容，框架本身的空格和命名冲突会让冷读来回振荡。
- **调研memo写法带进正文（2026-10-26）**：把事实/推断/未知标签和全部限定条件塞进同一句，会产生长定语和汇报口吻。同一根源的另一种形态是归属式限定：为了给推断「标口吻」，满篇「按我们的理解」「在我们看来」「我们认为」，作者问「整篇都是我们写的，为什么老要强调，是不自信吗」。文章本来就是作者的观点，判断直接陈述；需要区分事实和推断时，写清楚不知道什么、证据到哪一步，或用条件句。核查员不应把删掉这类限定报成漂移，lint 已把这些短语列为禁词。
- **出现交代工作过程的meta句（2026-10-26）**：比如`本次讨论由 2026 年 10 月 16 日生效的新版隐私政策触发`、`在查看……后发现`，读者不需要知道作者的工作过程。
- **主线程自己重写正文（2026-10-26）**：主线程按作者的反馈直接重写中文正文，作者评价很差，最终放弃。正文必须由Argon来起草和重写。
- **voice rewrite事实漂移（2026-10-26）**：曾经把迁移方向写反了（`AI Mode的格式可能会迁移到Gemini` 变成 `Gemini的东西挪到搜索`），`先后上线` 变`同时上线`，3月的`当时` 变`目前`，`可以用来` 变`也会被用来`，`目前不用于` 变`将不会被用于`，`高亮回答` 变`加粗答案`，以及截断链接锚文本（更早的实例见工作区的 voice rewrite overlay）。
- **voice rewrite带回禁词和破折号**：voice会把句子改长，加回`这意味着`，`很稳`等禁词和破折号，所以lint和冷读必须在voice之后的最终稿上跑。
- **thesis和近期文章重复（2026-10-25）**：同样的论点半年内写了三次，读者疲劳。
- **作者自己的认知更正被当成钩子（2026-10-26）**：开头写「我们以为 X，其实是 Y」，这个落差只对和作者有过同样误解的读者成立，门槛测试会超过两项。作者的更正放进正文当转折，两三句说完；入口换成读者自己的问题。
- **AGY权限拦截和进程挂住（2026-10-25）**：带`--dangerously-skip-permissions`会被权限分类器拦下，需要改用内联prompt加`--mode plan`。进程写完stdout可能挂住不退出，直接读`stdout.json`，不等进程结束。
- **初稿篇幅接近目标的两倍（2026-10-25）**：给Argon的prompt必须写明每节字数预算。

## 配图

长文配 2-3 张图（2000 字以下短文至少 1 张），用 GPT Image 生成或重绘（默认 `gpt-image-2.5-sunburst`），压成 JPG/WebP，长边约 1024px、单图小于 200KB，用相对路径，alt 写完整判断句。

### 生成前决策与视觉规范

在生成之前先问自己：这张图要做什么认知工作？说不出来就不生成：
1. **目标**：消歧（平息矛盾）、外化机制（梳理链条）、压平结构（一屏全景）三选一；删图若不损理解则不生成。
2. **落位**：紧贴支撑判断或矛盾初现处，相邻图表不重复同一信息，章首文末严禁放纯装饰图。
3. **内容**：一图一判断，优先承载数据，文字压至最少（2-6 字短标签或裸数字，整句不进图）。

无站点专属视觉规范时，必须执行以下默认规范，不得以"看起来更专业/更像编辑插画"为由替换：
- **构图三选一**：对比面板（A vs B）、传导链（3-5 节点因果）、分层全景（层级系统）。
- **语义配色**：奶油底 `#F6F2E7`、结构 `#6B7FE8`（线稿 `#8298FF`）、价值/钱 `#E8A33D`、负信号 `#C6574A`（线稿 `#C26B5A`，至多一处）、线字 `#2E3442`（线稿 `#3A4150`）。颜色按语义角色分配，不按好看分配：琥珀只给钱、价值、代价类对象，每图至多一组；普通对象需要区分时，用结构色的明度阶梯。
- **渲染二选一（同篇不混档）**：**像素档是强制默认**，用于机制隐喻和概念对比；**线稿档**只在精确标注数据、协议、政策时使用。
- **档位硬定义**：像素档整图只用 8-16 个纯色，色块平涂，边缘硬切，无抗锯齿、无渐变、无柔和阴影、无高光、无圆角发光、无 3D 斜面；线稿档为单色或双色等宽线描，文字和标注精确，无渐变和阴影。
- **Prompt 与骨架约束**：像素档 prompt 必须显式包含 `pixel art, flat fills, 8-16 colors, hard edges, no anti-aliasing, no gradients, no soft shadows, no glossy highlights`；禁止出现 `editorial illustration`、`cinematic`、`modern vector`、`soft shadow`、`gradient`、`glossy`、`3D`、`isometric`。matplotlib 或 SVG 只能画扁平版式骨架（无渐变、阴影、抗锯齿），最终文件必须由 GPT Image 重新生成或重绘。

生成后立即进行四步验收，不合格则重画：
1. 用 Pillow 统计像素档唯一 RGB 值，去噪后主色落在 8-16 个之间。
2. 放大到 200% 检查色块边界是否硬切，无灰阶过渡或模糊边。
3. 检查无柔和投影、高光或渐变。
4. 核对生成 prompt 含像素档关键词且无禁用词。
