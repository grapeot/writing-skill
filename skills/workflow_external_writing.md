# 外部写作与成文工作流（Operational Spine）

## 元数据

- **类型**：Workflow（操作主干）
- **适用场景**：把已核实的调研转化为 external-facing 中文分析文章、公开 survey report、课程或客户内容。
- **前置依赖**：`workflow_deep_research_survey.md` Phase 1-3 或等价事实底稿。
- **诊断词汇**：`bestpractice_external_prose.md`（Manager 查阅，非 gate 清单，不进 Writer 上下文）。
- **机械自查 CLI**：`external_prose_lint.md`（`external_prose_lint_cli.py`）。
- **最后更新**：2026-10-10

## 0. 这个文件的纪律

这是操作主干。这里的每一条要么是**工件规格**，要么是**可执行、能阻断的 gate**——不放展开性原则叙述（见 `bestpractice_external_prose.md`）。

来自五个写作 session 的硬教训：把同一条 prose 规则写进多处并让模型自评，规则不会生效。模型看得见症状，但自述式判定从不阻断。**gate 只有满足两条件才生效**：(a) 判定发生在一个看不到答案的上下文里；(b) verdict 由机器提取、由脚本阻断，不由 Main Agent 语感覆盖。本工作流用**多阶段强制全文重写管线**消除“教材声”与“AI 腔”，终局实行**“机械代码校验器 + 终端冷读”的双重硬阻断**。

## 1. 三种工作，不能同一个 context 做

1. **编辑判断**：文章为什么值得写，读者应改变什么认识，证据按什么顺序到达。
2. **完整成文与管线 naturalize 重写**：通过结构稿与独立 naturalize 重写将内容转化为自然连贯的 prose。
3. **结果验收**：事实漂移由重写前后的独立核查判定（§4 阶段二/四）；约束与声线由机械校验器与独立冷读共同判定。

Main Agent 是编辑、事实负责人和最终验收者，但**不是 prose 判定者**——判定交给看不到 contract 的独立冷读与确定性 CLI。Main Agent 不得凭个人语感点修 Writer 的 prose（错字/数字/路径等对照 source contract 唯一确定的机械修正除外）；品味判断问题回管线重跑。

**Writer 层级裁定规则（2026-10-03 裁定）**：任何 prose 只属于最近一次触碰它的 writer。独立 Writer 改写过的段落以其输出为准；voice rewrite 跑过的段落以 voice rewrite 输出为准。Main Agent 不得对 Writer 的风格说三道四，更不得按自己观点回改——有问题回管线重跑或摆给人类裁定；「感觉 AI 味重」只构成回管线或上报理由，不构成回改依据。

**例外仅限事实漂移与格式/结构恢复**：对照 `source_contract.md` / draft 出现事实漂移（数字、日期、归属、方向、强度、遗漏或新增事实）时，Main Agent 直接做 surgical fix（只改漂移点、保留 Writer 措辞与声线，不整段退回），在交付记录逐条列出修正；纯机械的格式与结构恢复见 §5.3。除此之外的任何措辞差异一律不碰。

### 1.1 执行载体与上下文隔离约束（Antigravity CLI）

初稿生成、naturalize 重写、事实漂移核查与盲读/终端冷读默认通过 Antigravity + Gemini 4 Argon High 完成，所有 harness 一致。严禁在 Main Agent 同一 context 里局部修正几行冒充重写或冷读。

先读 ai-agent-cli 根 skill 与 Antigravity focused skill；通用 CLI 技术说明留在那里，本工作流只保留任务特定的调用、隔离与超时要求：

```bash
agy --print "Read /absolute/path/to/minimal-scratch/prompt.md; follow it and write the required output artifact." \
  --model gemini-4-argon-high \
  --mode accept-edits \
  --sandbox \
  --dangerously-skip-permissions \
  --new-project \
  --print-timeout 10m \
  --output-format json \
  --log-file /absolute/path/to/minimal-scratch/events.log
```

- 控制 10 分钟任务超时；quota 错误立即停止，不盲目重试。每轮调用均为全新会话：必带 `--new-project`，不用 `--continue` / `--conversation`。
- 启动时 cwd 必须指向独立 minimal scratch，调用方不得向 child 加载父工作区或全局写作规则。
- scratch 仅放该阶段授权输入，以绝对路径引用。冷读只见正文与极简评测 prompt，不见 contract、brief、历史或全局规则。
- 成功必须同时满足 exit 0、stdout JSON `status: "SUCCESS"`，且输出工件非空、落在本次 scratch 并读回核验。执行成功不替代质量 gate。

## 2. 输出路由与交付边界

- 只说 external-facing：默认存 `contexts/survey_sessions/`。
- 明确说博客：存 `contexts/blog/content/`。
- 本地最终 Markdown 是写作终点，配图是交付的一部分（见 §6）。发布、排程、社交媒体等外发动作须等显式授权。

## 3. 写作前先选对文章

### 3.1 先提取初始请求里已播下的框架

动笔和立方案前，先复述初始请求中的已有要素。用户常在首句播下 thesis、主角、对立结构或读者定位；忽略它并径直收敛到自我感觉漂亮的机制结论，是最常见走偏。

### 3.2 准备契约工件

- **`source_contract.md`**：事实完整、不含推测。
- **`writing_brief.md`**：reader start state / 读者已有的关心与入口方案（见 §3.3）/ takeaway / 精确 thesis / H2 结构规划（4-6 个 `## H2`）/ 候选标题。
- **`audience_contract.md`**：读者已知与禁止假设的未知概念、单一带走点。
- **`voice_contract.md`**：目标 register 场景化描述（“坐在旁边”级别：平实具体不端着，短句落判断、长句连因果、段落有呼吸）；姿态范例；禁极性词与套路比喻。自指 before→after 样例不进 contract，由 Manager 在 naturalize 阶段从当次 draft 挑选（见 §4 阶段三）。
- **`content_map.md`**：非线性证据卡片映射（`body-essential` / `appendix-only` / `omit`）。

**来源链接纪律（硬要求）：** 调研得到的来源一律在正文就地嵌入（`[中文标签](url)`），供读者就地核查；不得只堆在文末参考资料、或只留在 scratchpad / search manifest。**不另设独立的参考资料来源章节。** 外部文章至少 3 个行内嵌入链接。

### 3.3 开头纪律：先回答读者为什么要读

开头（标题、H1 导语与首个 H2）的首要任务是回答读者为什么想读；场景、抽象问题、领域观察都只是切入手段。开头的构思与正文成稿同等量级投入。违反任一条即判不合格，回炉重跑：

1. **入口接在读者已有的关心上**：`writing_brief.md` 写明读者是谁、他此刻已在关心什么（他自己的问题，不是我们的话题）、我们从哪一点接上；至少比较两个入口再选。**门槛测试**：列出读者须同时满足哪些前提才会被开头吸引（如「用过语音助手 × 了解其内部 × 对此好奇 × 关心推理基础设施」），超过两项即换入口。入口必须是正文兑现的东西，不得以诱饵换题。
2. **标题自明**：读者初见即懂在讲什么。必须有显式主语与张力，不出现无测量对象的数字、行话或自造词（自造词可放后半，前半须有主语与钩子）。
3. **earn-the-next 规则**：导语和首个 H2 每句话都必须让读者建立正确预期或给出读下去的理由，否则删改；逐句核对读者所获（认知预期/数据源/反直觉事实/自身关联），写不出即不合格。背景、融资、创始人经历不是理由。利益冲突披露须与数据可信度讨论同段呈现，成为论证的一部分，不置于文首。
4. **setup before numbers**：数字首次出现前，必须先交代测量对象、测量者与测试 setting。未建上下文的纯数字是认知负债。

### 3.4 正文逻辑纪律：先讲为什么，伏笔必须回收（教材评审反馈，2026-10）

§3.3 管开头，本节管全文。长文常见毛病是逻辑跳跃：结论先于对象、铺垫脱节、话题来回切。四条规则：

1. **每节先回答“为什么要关心”，再讲做什么。** 先写读者的第一反应与自然质疑并正面回应；why 往往比 what 更重要。
2. **对象先于评价。** 未介绍对象前不评价好坏。顺序：是什么 → 解决什么问题 → 做得怎样（评价须有具体所指）。
3. **伏笔必须回收（契诃夫之枪）。** 承上启下；文中提出的数字、问题与承诺后文必须闭环，用不到即删。抽查法：每段须能说明承接上文哪一句、为下文铺垫什么。
4. **顺序与详略。** 避免同一主题来回跳跃；主线给足篇幅，旁支压成单句或括号说明。

参照物：若同一主题有讲稿或 slide deck，可对照其经现场验证的叙事顺序检验逻辑。

### 3.5 中文句子层常见病（教材评审反馈，2026-10）

这些是 lint 抓不全、但读来别扭的句子层问题。修改由 naturalize Writer 执行（样例口径见 §4 阶段三），Main Agent 不自行点改句式。**时机：本表与 §3.4 问题均在进 voice rewrite（§5.3）前改完；voice rewrite 之后若改写稿把某处改回，以 voice 输出为准（§5.3）。**

| 病 | 原句（真实样例） | 改法 |
|---|---|---|
| 单字口语动词/补语（AI 腔） | 几个例子看不出；同样输入比比；把话扔给它；提前攒一大批；从里面捞 Yes 或 No；把答案抠出来；预算扛不住；蒸馏造不出；只想在本地看看 | 换双音节表达：很难从几个例子中看出来；用同样的输入加以比较；交给它/发给它；收集一大批；提取 Yes 或 No；提取答案；承受不了；没法凭空造出来；看一下结果 |
| 翻译腔 | 理解它为什么长成这样（出生时面临什么限制） | 弄清楚是哪些因素、哪些限制让它设计成了现在的样子 |
| 被动语态排比（passive parallelism） | 能力被 agent 调用、被 agent 组装、被 agent 运营 | 让动作主语回到句首：agent 可以调用公司的能力、组装公司的能力、运营公司；「被团队使用、被客户验证」改成「团队使用这些工具，客户验证它们」。连续 ≥3 个「被」或「被…、被…」一律改，单个「被」仍由 lint 的 `bei_passive` 提示 |
| 病句：缺主语/主题不清 | 不过第一个问题没过的，大都是包装 | 如果一样东西过不了第一个问题（即模型强十倍后不再重要），那它多半是包装 |
| 英文直译比喻 | 没人会帮你剥包装 | 没人会帮你拆开包装 |
| 夸张类比 | 看上去像是一种新物种 | 看上去像是一种全新的模型 |
| 判断强度标错 | 这两句话现在还是判断 | 这两句话现在还是主观判断（推测须标明推测） |
| 描述不完整 | 聊天模型往往先写一大段话 | 往往先写一大段话或做很长的思考（说全已知情况） |
| 容器称呼错 | 我们在这本书里拿它来举例 | 用真实载体名：在这一节 / 这个 module 里 |
| 旁支事实逗号硬接 | 而且很便宜，后面我们让它玩一整局吃豆人，花费不到一美分 | 旁支放括号：而且很便宜（后面……不到一美分） |
| 英文语序：状语/受益对象后置 | 注册一个 API key 给它（register a key for it） | 状语前置：帮它注册一个 API key |
| 英文直译判断句 | 这个需求是个选择题；学完你会带走什么；首先准备两个材料；这里还有一个很好的机会 | 这类需求有一个共同点：要在几个选项里挑一个；学完后你手里会有什么；开始前准备好两样东西；不妨再多走一步 |
| 贯穿全文的生造比喻 | 先做一把尺子；有了尺子才能比较 | 直接说事：先把测量方法定下来；能测量了才能比较 |
| 词语暗示错误 | 它自己编了 8 条评价（读者会以为是幻觉） | 它自己构建了 8 条虚拟的评价 |
| 来源说错 | 和网上说的 115 毫秒是同一个量级（115 实为自测） | 分清官方与自测：官方给出 70-500 毫秒，我们实测约 115 毫秒 |
| 口语化“硬”字评价 | 最硬的一条是…… | 其中最关键的一条是…… |
| 句尾缺语气（电报体） | 到这里就可以结束；它们不再必要 | 到这里就可以结束了；它们就不再有必要 |
| 能用贴切成语却用长描述 | 往往只见树木不见森林 | 贴切时用成语（如管中窥豹，只见一斑），不贴切不硬凹 |

## 4. Round 2：多阶段成文管线

成文不走“一步到位”或盲目微调，通过多阶段独立上下文消除 AI 腔和教材声。结构稿负责事实与结构，naturalize 重写负责 register 且 prompt 只装单一 voice 目标（两次写作 session 实测：带 10-11 项事实修正清单的多目标重写产物落在报告腔、没过人工审阅，不带清单的单目标 naturalize 产物通过）；事实修正在重写前后各有独立机械 pass；文风由 §5 双重 gate 判定。

1. **阶段一：结构稿（`draft.md`）**
   - Main Agent 将 brief、content map、source contract 放进 minimal scratch，委托独立 Antigravity CLI 生成结构完整的 `draft.md`，不手写正文 prose。重点是保真事实、建立概念依赖与铺设 carrier。
2. **阶段二：Manager draft 事实回查（Main Agent，机械）**
   - Main Agent 读回 `draft.md` 对照 source contract 逐条回查事实、数字、URL 与 claim 强度。唯一确定的机械错误就地修正；涉及强度或结构判断回阶段一重跑。确保 naturalize prompt 不背负任何事实纠错清单。
3. **阶段三：naturalize 重写（`naturalize.md`，不可跳过）**
   - 另起全新独立 Antigravity CLI 会话，从头重写为平实自然 prose，写入 `naturalize.md`。prompt 仅装单一 voice 目标，不含事实纠错与结构改动。
   - prompt 包含：`voice_contract.md` 场景化 register 描述与节奏要求；Manager 从当次 draft 挑选并改写的 1-3 个真实病灶句 before→after 样例；硬保留清单（顺序、H1/H2 结构、全部事实/数字/链接、占位符、判断强度、人称边界、篇幅容差 ±10%）。写完即结束，不自查、不输额外内容。
4. **阶段四：事实漂移核查 + surgical fix（独立上下文）**
   - 另起全新独立上下文将 `naturalize.md` 逐段对照 `draft.md` 与 source contract，列出事实漂移。
   - Surgical fix：只将漂移点机械改回原基准表述，不动声线与节奏。漂移过大时不就地修补，回阶段三重跑同一 prompt；同一漂移复现则回阶段二或一排查。
5. **阶段五：Manager Mechanical Pass**
   - Main Agent 读回修订全文，仅修正唯一确定的机械错误（错字、数字、路径等）。品味判断问题回阶段三/四重跑，不自行改写，严守 §1 边界。

## 5. 双重终局 Gate（机械代码校验器 + 终端冷读）

文章落盘至 canonical Markdown 后，必须顺次通过以下两道硬阻断 Gate：

### 5.1 Gate 1：机械代码校验器（`external_prose_lint_cli`）

终端运行确定性扫描工具：

```bash
.venv/bin/python -m writing_skill.external_prose_lint_cli path/to/article.md
```

- **阻断标准**：贴出完整 stdout；回答所有 FINDINGS 并修改，直到 `hard_findings=0` 且 exit code 为 `0`。自述“没问题”但未贴 stdout 直接判失败。
- **覆盖项**：破折号 `——`、概念词引号、括号补译、评价标签（“很…：”）、极性词、元评论铺垫、不是 X 而是 Y、稳定禁词表、单句段、被动“被”字句、被动语态排比（连续 ≥3 个「被」或「被…、被…」）、英文词密度（>20/段）、同一 URL 重复（>2 次）、域名锚文本、数字认知负担（WARNING：单段 ≥5 或连两段各 ≥3 触发）等。
- 执行 §5.3 的 voice rewrite 之后，本 Gate 降级为只读报告，见 §5.3。

### 5.2 Gate 2：不可 Overrule 的终端陌生读者冷读（Terminal Cold Read）

通过 Gate 1 后，另起全新独立 Antigravity CLI 会话（minimal scratch 仅含最终正文与极简评测 prompt，隔绝 brief、contract 与历史）：

- **评测输出**：(1) 读者姿态体感（同行分享 vs 高高在上）；(2) 无术语复述测试（能否通俗复述每节）；(3) 逻辑断点（未介绍即评价、伏笔未收、话题跳跃、前后脱节）；(4) 入场理由（评测 prompt 只附一句目标读者身份、不含 thesis；冷读者只读标题和导语后，以该身份说出自己为什么会继续读）。
- **硬阻断 Verdict**：必须以固定格式输出 `TERMINAL_VERDICT: SHIP` 或 `TERMINAL_VERDICT: BLOCK`（附原因）。姿态不当、复述失败、存逻辑断点，或说不出入场理由、理由要靠多重前提才成立，即输出 `BLOCK`，必须打回管线修正，无豁免权。

### 5.3 终局可选步骤：作者文风改写（voice rewrite）

Gate 2 判定 `SHIP` 后，若工作区含 `voice-lora-rewrite` 且服务连通，则按该 skill 对 canonical Markdown 执行逐段改写（条件不备则跳过并说明；不替代阶段三）。**Main Agent 只对事实负责，不对文风负责（2026-10-04 强调）。** Main Agent 辨别力弱于专用模型，无权评判或回改 voice 输出的文风（用词、句式、比喻、口语化、中英混用）；有异议只能重跑或交人类裁定。

改写产物不能直接交付：Main Agent 须逐段核对。**错漏事实必改（事实类）；破坏格式恢复原结构且不动文字（结构类）**；其余保留改写措辞与节奏，不整段退回改写前。文风与起承转合只记录呈报，不据此回改。若某段彻底破坏无法局部修整，才恢复该段内容（内容以原稿为准，尽量保留改写声线）。

**voice 之后 Gate 1 降级为只读报告（2026-10-04）。** 因 Gate 1 检测项多为文风信号且以 voice 为准，此时不再阻断。跑一遍 `external_prose_lint_cli` 将结果如实呈报；事实与结构类问题必改，句式与标点类仅报告，不再要求 `hard_findings=0`，由人类决定交付、重跑或微调。在 voice rewrite（§5.3）之前，Gate 1（§5.1）仍是阻断式硬 gate，保持不变。

## 6. 配图

短文（<2000 字）≥1 张，长文 ≥2-3 张。进最终 Markdown 的图须由 `gpt-image-2` 生成/重绘，压为 JPG/WebP，长边约 1024px、单图 <200KB，具相对路径与完整判断句 alt。

### 6.1 生成前决策与视觉规范（硬门槛）

每张图生成前须过三问；答不上来者不生成：

1. **目标**：消歧（平息矛盾）、外化机制（梳理链条）、压平结构（一屏全景）三选一；无认知工作则不生成。
2. **落位**：紧贴支撑判断或矛盾初现处；章首文末严禁放纯装饰图。
3. **内容**：一图一判断；优先承载数据，少用纯概念装饰；文字压至最少（2-6 字短标签或裸数字，整句不进图）。

**赚位置测试**：删图若不损理解则不生成；相邻图表不重复同一信息。
**反模式（出现即重做）**：无数据无判断装饰、与紧邻表格重复、章首文末配图、一图塞两判断、图内含整句文字。

视觉风格是硬门槛，不是建议。先确认站点视觉规范，只有站点明确写了规范时才按站点执行。没有站点规范时，下面这套默认规范必须执行，不得用「看起来更专业」「更像编辑插画」之类的理由替换。图像模型的默认审美会偏向平滑插画，不把约束写死，输出就会漂移。

- 构图三选一：对比面板（A vs B）、传导链（3-5 节点因果）、分层全景（层级系统）。
- 语义配色：奶油底 `#F6F2E7`、结构 `#6B7FE8`（线稿 `#8298FF`）、价值/钱 `#E8A33D`、负信号 `#C6574A`（线稿 `#C26B5A`，至多一处）、线字 `#2E3442`（线稿 `#3A4150`）。
- 渲染二选一，同篇不混档。**像素档是强制默认**，用于机制隐喻和概念对比；**线稿档**只在精确标注数据、协议、政策时使用。除这两种档位外没有第三种合法风格。

像素档的硬定义：整图只用 8-16 个纯色，色块平涂，边缘硬切，无抗锯齿、无渐变、无柔和阴影、无高光、无圆角发光、无 3D 斜面。出现其中任何一项即判不合格。线稿档的硬定义：单色或双色线描，线条等宽，文字和标注精确，无渐变和阴影。

生成前必须先把本节约束写进 prompt，不能只放在脑子里。像素档的 prompt 必须显式包含 `pixel art, flat fills, 8-16 colors, hard edges, no anti-aliasing, no gradients, no soft shadows, no glossy highlights`。禁止在 prompt 里出现会把模型拉向平滑插画的词：`editorial illustration`、`cinematic`、`modern vector`、`soft shadow`、`gradient`、`glossy`、`3D`、`isometric`。matplotlib 或 SVG 只能用来画扁平的版式骨架（色块和文字位置），不得作为最终交付，也不得把渐变、阴影、抗锯齿带进骨架；最终文件必须由 GPT Image 按上述档位重新生成或重绘。

生成后立刻验收，不合格就重画，不得带病进入 Markdown：

1. 数颜色。像素档用 Pillow 统计唯一 RGB 值，去噪后主色应落在 8-16 个；明显超出即不合格。
2. 看边缘。放大到 200% 检查色块边界是否硬切，出现灰阶过渡或模糊边即不合格。
3. 看阴影和高光。出现柔和投影、发光、渐变即不合格。
4. 对照 prompt。确认生成时用的 prompt 含像素档关键词，且没有禁用词。
5. 档位、配色、构图没定下来就不生成。先定约束，再写 prompt，再生成，顺序反了就会顺着模型默认审美走。

## 7. 交付

在双重 Gate 通过（若执行了 §5.3 的 voice rewrite，Gate 1 按其降级口径，见 §5.3；Gate 2 须为 `SHIP`）后：
1. 向用户提供清晰的最终文件路径与残余风险说明（含 §5.3 是否执行）。
2. **交付即触发读取**：每次成稿或修改落盘后，Main Agent 必须立刻用 `view_file` 或 `read` 从开头读取全文并肉眼检查，确保用户端能直接预览最终版本，并在回复中给出路径；只写文件不触发读取不算交付。
